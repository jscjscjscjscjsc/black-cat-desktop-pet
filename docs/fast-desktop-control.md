# 更快的桌面控制与内存边界

## 当前执行优先级

1. **UIAutomation 结构化控件**：读取控件名称、AutomationId、ControlType，优先使用 `InvokePattern`、`ValuePattern` 或 `SetFocus`。这条路径不需要每步截图，也不需要视觉模型猜坐标。
2. **已观察窗口的键盘和鼠标**：只能在最近 30 秒的截图观察 ID 和前台窗口未变化时发送；输入后必须重新观察。
3. **视觉模型定位**：UIA 无法识别自绘控件、画布或游戏画面时才使用。

新增的 `computer(action=uia)` 支持 `invoke`、`set_value`、`focus`，控件没有可调用 Pattern 时才回退到控件中心点击。工具仍返回 `needs_observe=True`，因此执行账本不会直接把它当成完成，必须再调用 `accessibility` 或 `observe` 验证。

## 为什么不把所有软件都改成直接写内存

普通软件没有稳定的公开对象布局；版本更新后，偏移、对象关系和线程同步都可能改变。直接写内存需要同时知道目标版本、对象地址、生命周期和写入后界面状态，错误不会自然表现为“失败”，而可能静默破坏数据。UIA 是 Windows 提供的正式可访问性接口，通常更快也更稳定。

## 炉石的特殊路径

- HearthMirror 通过反射读取当前棋盘、卡牌 ID、实体 ID 和位置，属于只读集成。
- `memory_execution_available` 仍为 false；没有把读取能力包装成“已经能写内存执行”。
- 要实现直接动作，需要针对固定客户端构建版本验证对象地址、调用入口、参数和回执，并且每个动作都要有日志确认。
- 当前更可靠的路径仍是 Power.log 产生合法候选，视觉定位坐标，窗口输入，最后由日志 `SendOption` + 状态变化确认。

速度优化的优先级是：缓存 UIA 控件、减少不必要的截图和模型轮次、把只读观察批量合并、同一窗口保持焦点；只有在获得明确版本绑定和可验证回执后，才增加受控内存执行适配器。
